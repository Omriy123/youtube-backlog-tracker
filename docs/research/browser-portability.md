# Desktop browser portability

Checked 2026-10-13 against official Chrome, Mozilla, and Microsoft extension documentation. Scope: the proposed backlog's context menu, toolbar, library page, tab/group handling, and local persistence. This is API feasibility research, not an implementation estimate or a promise of tested support.

## Five implications

1. **A shared WebExtensions codebase is a reasonable design target.** Mozilla explicitly aims at compatibility while documenting API and manifest differences. Microsoft says Chrome APIs and manifest keys that Edge supports are code-compatible and recommends API review plus sideload testing. This supports shared core logic and UI, with browser-specific integration tested separately; it does not establish that an untested Chrome package already works everywhere. [Mozilla incompatibilities](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Chrome_incompatibilities), [Microsoft porting guidance](https://learn.microsoft.com/en-us/microsoft-edge/extensions-chromium/developer-guide/port-chrome-extension), [Edge API support](https://learn.microsoft.com/en-us/microsoft-edge/extensions/developer-guide/api-support)

2. **The proposed basic interactions have common APIs.** Firefox keeps `contextMenus` as a cross-browser alias for its `menus` API. Chrome documents page/link contexts and supplies the clicked link URL, fitting a save-video-link command. Both browser families support toolbar HTML popups and creating tabs for packaged extension pages; tabs can be queried, opened, moved, updated, and removed. A full library in an extension tab and a small toolbar popup therefore fit the common platform. Popup lifetime and sizing still matter: Mozilla documents destruction when closed, and Chrome documents a maximum size of 800 by 600 pixels. [Mozilla menus](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/menus), [Chrome contextMenus](https://developer.chrome.com/docs/extensions/reference/api/contextMenus), [Chrome action](https://developer.chrome.com/docs/extensions/reference/api/action), [Mozilla popups](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/user_interface/Popups), [Mozilla extension pages](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/user_interface/Extension_pages), [Chrome tabs](https://developer.chrome.com/docs/extensions/reference/api/tabs), [Mozilla tabs](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Working_with_the_Tabs_API)

3. **Native tab groups no longer force Chrome-only scope.** Firefox 139 added the `tabGroups` API; Chrome documents it from Chrome 89. Both use `tabs.group`/`tabs.ungroup` for membership and `tabGroups` for group state. However, group IDs are runtime references: Chrome scopes them to a browser session, and Mozilla warns that restored groups may have different IDs. Firefox private-window groups do not persist across restart; moving groups also has placement/window restrictions. Inference: capturing a currently open group is feasible across modern desktop browsers, but the backlog must retain its own saved grouping and links instead of treating a native group ID as a permanent queue identity. This research does not establish APIs for enumerating every browser's closed/saved groups. [Firefox 139 release notes](https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Releases/139), [Mozilla tabGroups](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/tabGroups), [Mozilla group moves](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/tabGroups/move), [Chrome tabGroups](https://developer.chrome.com/docs/extensions/reference/api/tabGroups)

4. **Background execution is a concrete portability seam.** Manifest V3 Chrome uses an extension service worker; Firefox currently uses background scripts/event pages and does not support `background.service_worker`. Mozilla documents a manifest containing both `scripts` and `service_worker` for modern browser versions, including relevant historical version restrictions. Chrome workers can stop when idle, so long-lived global variables are not durable state. Inference: shared event-handling logic should be compatible with suspension and the worker environment, while packaging accounts for each browser's background entry point. This is a specific engineering and validation task, not evidence that Firefox requires a second application. [Mozilla background manifest](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background), [Chrome worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)

5. **Common storage APIs do not provide cross-browser backup or sync automatically.** `storage.local` exists in both, but quota behavior differs: Chrome's own current documentation says 10 MB by default; Firefox follows IndexedDB-related limits. Both normally clear local extension data upon uninstall. MDN's storage.local page still gives an older 5 MB Chrome figure, so the Chrome-owned documentation takes precedence for Chrome. `storage.sync` uses each browser's account ecosystem, has small quotas, and Firefox requires an extension ID. Inference: common local persistence is feasible, but moving a library between Chrome and Firefox needs an explicit portable export/import or separately designed synchronization mechanism. [Chrome storage](https://developer.chrome.com/docs/extensions/reference/api/storage), [Mozilla local storage](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/storage/local), [Mozilla sync storage](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/storage/sync)

## Scope boundary

The evidence supports designing for modern desktop Chrome/Edge/Firefox with shared WebExtensions code. It does not justify a numeric effort estimate or a simultaneous-release guarantee without a working extension and browser tests. A Chrome-first release can preserve that portability target. Safari, mobile browsers, closed-group recovery, store distribution, and every browser-specific media-page behavior were outside this bounded check.
