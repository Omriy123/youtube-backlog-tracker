# Design constraints follow-up

Checked 2026-10-13 against first-party documentation. Supplements [browser portability](browser-portability.md), [YouTube metadata and identity](video-metadata-and-identity.md), and [tab-manager recovery](tab-manager-recovery.md). These are documented capabilities and constraints, not user decisions or tested integration behavior. No credentials or live API requests were used.

## Browser scope and persistence

- Modern desktop Chrome and Edge support native tab-group integration. Microsoft explicitly lists `tabGroups` for Manifest V3 on Windows, Linux, and Mac. Firefox added its `tabGroups` API in version 139. [Edge API support](https://learn.microsoft.com/en-us/microsoft-edge/extensions/developer-guide/api-support), [Firefox 139](https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Releases/139), [Chrome tabGroups](https://developer.chrome.com/docs/extensions/reference/api/tabGroups)
- Native group IDs are not permanent Library identities: Chrome guarantees uniqueness only within a browser session; Firefox may assign a different ID after session restore. Capturing group names and member links into the Library is therefore a supported design direction, while enumerating closed/saved groups remains unverified. [Chrome group IDs](https://developer.chrome.com/docs/extensions/reference/api/tabGroups), [Firefox restoration](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/tabGroups)
- The existing background distinction remains current: Chrome Manifest V3 uses a service worker; Firefox does not support `background.service_worker` and uses scripts/event pages. Mozilla documents a manifest fallback containing both entries for modern browsers. Chrome workers can terminate while idle, losing global variables. [Background manifest](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background), [Worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)
- Chrome `storage.local` has a default 10 MB limit, enlarged with `unlimitedStorage`, and is deleted on extension removal. Firefox follows IndexedDB storage limits, with disk-wide limits still possible even with that permission, and ordinarily clears storage on uninstall. Chrome sync storage is approximately 100 KB total/8 KB per item and belongs to the Chrome account ecosystem. Inference: local history or snapshots need an external surviving copy to protect against profile/device loss; these APIs do not establish cross-browser Library sync. [Chrome storage](https://developer.chrome.com/docs/extensions/reference/api/storage), [Firefox local storage](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/storage/local)

Browser API feasibility supports a shared application with browser integration differences. It does not establish an effort estimate or release-support guarantee without browser tests.

## YouTube metadata lifetime and identity

The previously recorded constraint is confirmed: Developer Policies III.E.4.c-d require applicable stored metadata to be refreshed or deleted after 30 calendar days, including limited non-authorized data. III.E.4.e-f require reasonable consistency efforts and current presentation; historical presentation is not an explicit retention exemption. III.E.6 prohibits API clients from scraping YouTube applications or obtaining scraped data. The section numbering is **III.E.6**, rather than III.E.5 in the older note. Inference: indefinite retention of inaccessible API-derived title/description snapshots is not an established unrestricted capability; metadata copies in recovery/export also need a defined source/lifetime contract. Labeling a copy historical or user-owned does not establish an exemption. [Developer Policies](https://developers.google.com/youtube/terms/developer-policies)

Official documentation establishes several URL identity forms:

| Form | Documented identity |
| --- | --- |
| `youtube.com/watch?v=VIDEO_ID` | The `v` value identifies the video, including when a timestamp parameter follows. [Google video identifier](https://developers.google.com/google-ads/api/reference/rpc/v22/YoutubeVideoIdentifier) |
| `youtu.be/VIDEO_ID` | YouTube's own short URL contains the same video ID and redirects to that video. [YouTube engineering announcement](https://blog.youtube/news-and-events/make-way-for-youtube-links/) |
| `youtube.com/embed/VIDEO_ID` | The embed path contains the video ID. Playlist embeds may instead have no individual video ID. [Player URL documentation](https://developers.google.com/youtube/player_parameters) |

Inference: normalize recognized forms to provider plus video ID for same-upload duplicate detection; timestamps and playlist context do not create a new upload. This check did not find an authoritative exhaustive parsing contract for Shorts, `/live/`, mobile/music hosts, redirect wrappers, or every sharing parameter. Those forms can be product requirements, but need representative fixtures and explicit validation instead of an assumption that every YouTube-domain URL is a single video. The official public API does not promise that a missing resource reveals whether it was deleted, private, or otherwise inaccessible. [videos.list](https://developers.google.com/youtube/v3/docs/videos/list)

## Twitch VOD metadata and credentials

`GET /helix/videos` requires an app or user OAuth access token and matching `Client-Id`. It accepts known video IDs and returns the video's `id`, broadcaster identity, title, description, creation/publication dates, URL, thumbnail URL, type, and duration. Its example pairs a numeric ID with `https://www.twitch.tv/videos/ID`. A missing ID is ignored in a mixed successful batch; all missing IDs produce documented 404 behavior. The resource ID identifies the video; no indefinite playback or metadata availability is promised. [Get Videos](https://dev.twitch.tv/docs/api/reference/#get-videos)

An app access token uses the client-credentials flow, requiring a registered client ID and **client secret**. Twitch describes this as server-to-server use. Twitch permits embedding the public client ID but explicitly forbids exposing the secret to users, even obscured. Client-side user-token flows are documented and require user authorization; maintained OAuth sessions require token validation. Inference: a distributed local-only extension cannot safely bundle the secret to promise silent app-token metadata lookup. Choose a supported user-authorization flow, a service that keeps the secret confidential, or a reduced metadata contract. These are alternatives for the interview, not selected architecture. [Token flows](https://dev.twitch.tv/docs/authentication/getting-tokens-oauth/), [App registration and secret rules](https://dev.twitch.tv/docs/authentication/register-app/)

Twitch's embed player uses a `video=vID` parameter for past broadcasts/highlights/uploads; channel URLs identify live channels instead of one durable VOD. Inference: record provider plus VOD ID separately from channel identity and playback timestamps. [Video/embed parameters](https://dev.twitch.tv/docs/embed/video-and-clips/)

## Grouped tab-manager imports

Session Buddy explicitly publishes collection export formats: JSON with `collections -> folders -> links`, CSV with collection/folder/title/URL columns, and indented grouped text. JSON/CSV preserve documented collection/folder grouping; flat URL formats do not. Export JSON also lists numeric `groupId` but no full native-tab-group name/color schema, so collection/folder preservation must not be confused with guaranteed native-group preservation. [Supported formats](https://sessionbuddy.com/formats/)

Its collection Import/Export excludes history; Backup/Restore includes history and serves recovery. Inference: importing Session Buddy collections into this Library should name supported collection-export formats explicitly. Supporting its complete backup file would be a separate compatibility contract, not implied by reading the documented export hierarchy. [Import/Export distinction](https://sessionbuddy.com/import-export/), [Backup/Restore](https://sessionbuddy.com/backup-restore/)

OneTab officially offers export/import and recommends exports for recovery, but the first-party homepage/help/troubleshooting pages checked do not publish a complete export grammar or establish which current format preserves named groups, folders, notes, dates, or tasks. Claims about `URL | title` lines and blank-line groups came from third-party tools and were excluded. Inference: preserve OneTab import as a requirement while making its exact compatibility contract depend on a representative export from the user's installed version. [OneTab homepage](https://www.one-tab.com/), [Help](https://www.one-tab.com/help), [Troubleshooting](https://www.one-tab.com/troubleshooting)

## Early metadata contract validation

Rechecked 2026-10-14 for the [first save/find/open/recover slice](../design/feature-map.md). This section records source boundaries and unanswered policy mechanics, not legal conclusions or selected behavior.

- **API origin has a published definition.** API Terms section 1 defines API Data as data/content/information supplied through YouTube API services. API Terms 24.3 requires deletion of API Data in the developer/client's possession or control following suspension/discontinuance/termination. Neither clause supplies a transformation rule for imports, relabeling, or manual edits. Inference: preserve factual acquisition origin; do not claim a copied API title becomes independently authored merely because the user imports or renames its field. Meaningful user rewriting and copies held solely by a user are not specifically adjudicated here. [API Terms](https://developers.google.com/youtube/terms/api-services-terms-of-service)
- **Historical presentation is distinct from retention.** Policies III.E.4.c-d require applicable metadata refresh/deletion within 30 calendar days; III.E.4.f permits accurately contextualized historical display without stating a retention exemption. No metadata-specific snapshot/export/restore exemption or lifetime-reset rule was found. III.E.1.a's explicit backup restriction concerns audiovisual content, not a general prohibition on metadata backup. Published clauses do not specify how an offline user-held metadata export must be purged or how restoring an older snapshot interacts with successful refresh. III.E.4.h requires clear distinction when presenting independent product data alongside API Data; it does not establish that relabeling/editing cancels origin or lifetime. III.E.6 prohibits API-client scraping and obtaining scraped YouTube data; no explicit browser-tab-title capture exception is stated. [Developer Policies](https://developers.google.com/youtube/terms/developer-policies)
- **The analytics extension does not extend title retention.** The current additional policy allows approved statistical/derived metrics storage up to 36 months, but explicitly keeps video titles, creator names, descriptions, and comment text under the 30-day refresh/deletion policy. This is a useful direct confirmation, even for applications qualifying for that separate exception. [Additional policy, Data Storage](https://developers.google.com/youtube/terms/derived-metrics-policy)
- **Browser capture and DOM extraction are different technical paths.** Chrome `tabs.Tab` supplies a browser tab's title and last committed main-frame URL; `tabs`, matching host permission, or temporary user-invoked `activeTab` access enables relevant properties. The title is optional, and a URL may be empty before navigation commits. These are not a YouTube Data API response or a complete metadata resource. [Tabs API](https://developer.chrome.com/docs/extensions/reference/api/tabs)
- A context-menu event supplies `linkUrl` for a clicked link, separately from `pageUrl`; its schema does not promise a linked video's title. Content scripts separately read page details through the DOM. Browser API availability establishes technical capability, not permission under provider policies. YouTube's general Terms also restrict automated service access; the checked terms do not specifically classify saving existing browser tab properties through a user-invoked extension action. Thus neither applying the API's 30-day rule to every browser-sourced title nor declaring every page-observed value exempt is established by these sources. [Context-menu fields](https://developer.chrome.com/docs/extensions/reference/api/contextMenus), [Content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts), [YouTube Terms, Permissions and Restrictions](https://www.youtube.com/static?template=terms)

Evidence supports keeping browser-captured, API-fetched, deliberately authored, application-generated, and unknown imported origins distinct. The field contract should record the chosen recovery behavior rather than describe unresolved export/edit/capture interpretations as verified provider guarantees. This research does not establish that saving and organizing user links requires optional API enrichment.

The `/live/` example is published by YouTube itself, but is not a normative URL grammar. Twitch identifies the video separately from broadcaster and stream IDs. [YouTube event link](https://blog.youtube/intl/ja-jp/news-and-events/maj-2026-with-creators/), [Twitch Get Videos](https://dev.twitch.tv/docs/api/reference/#get-videos)

Include boundary examples alongside recognized forms: a playlist URL without a video ID, channel/search pages, a Twitch channel or clip URL, malformed IDs, conflicting repeated `v` parameters, and lookalike hosts such as `youtube.com.example.org`. They should not accidentally identify a single known upload. Exact acceptance and opening-context rules remain foundation/capture contracts; recognizing URL syntax does not prove present playback availability.

Session Buddy officially represents `collections -> folders -> links` as ordered arrays and exports `titleOriginal` when a title was edited. Its documented fields do not carry the original title's acquisition source or provider-fetch time; text export may substitute `Untitled`. [Session Buddy formats](https://sessionbuddy.com/formats/)

Three synthetic scenarios expose relevant foundation contracts without requiring an import parser in the first slice:

1. **Repeated upload within one group.** Collection `Learning`, folder `Queue`, link 1 `{ "title": "Example lecture", "url": "https://www.youtube.com/watch?v=M7lc1UVf-VE" }`, link 2 `{ "url": "https://youtu.be/M7lc1UVf-VE?t=120" }`. Exercise one upload identity while retaining two input occurrences and their order for later accounting. The second occurrence has no title, not an authored empty title.
2. **Repeated upload among groups.** `Learning/Queue` contains that watch URL first; `Weekend/Picks` contains its short-link variant second, then Twitch `/videos/335921245`. Exercise provider-separated identity and preserved source group/occurrence order without giving the same saved video two active destinations. Source order is not automatically publication order or list importance.
3. **Title edit evidence versus unknown source.** A JSON link has `title: "My short label"` and `titleOriginal: "Example lecture"`; a CSV/indented-text link has only `Title: "Example lecture"` or `Untitled`. The JSON demonstrates an edit in the source application; neither format proves whether the original text was browser-captured, API-fetched, or deliberately written. Do not silently classify every imported title as user-authored or treat `Untitled` as authoritative video metadata.

Foundation owns upload identity and exclusive-placement invariants; capture owns repeat-save interaction and opening-context choices; imports owns eventual source conversion, accounting, and batch review. These examples inform those boundaries rather than deciding their interfaces.
